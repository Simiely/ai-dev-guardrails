# 使用指南：把模板包接进项目并跑起第一个任务

这份指南面向人。给 AI 的操作手册是 [执行说明](../pack/docs/EXECUTION.md)，两份分工不同：

- 本页：怎么装、怎么开始、每个文件干什么
- 执行说明：每个任务具体怎么执行

## 0. 先判断要不要用

| 适合 | 不适合 |
|---|---|
| 会持续迭代一个月以上的项目 | 一次性脚本 |
| 需求会反复变 | 纯探索原型 |
| 出现过多轮修改后失控 | 需求还不存在的阶段 |
| 有第二个人要看代码 | 只跑一次的 demo |

小项目不用全套：只用 T0 流程加三条 CI 检查就够，其余模板空着不填。

## 1. 一次性安装

### Step 1 · 复制

把本仓库 `pack/` 里的内容复制到项目根目录。

如果项目已有 `README.md`，不要覆盖；把本页的「快速开始」抄过去即可。

### Step 2 · 填宪法

打开 `ARCHITECTURE.md`，填 1–6 节：

- 第 1 节：系统一句话
- 第 2 节：模块清单与依赖方向
- 第 3 节：公共契约在哪
- 第 4 节：数据和安全的边界
- 第 5 节：质量底线
- 第 6 节：禁止清单

填不出来的地方，就是还没想清楚的架构。先标 `<TODO>`，不要编。

### Step 3 · 定依赖方向

改 `registry.yaml` 的 `dependency_direction`。不知道怎么写就先用最小版本：

```yaml
dependency_direction:
  - ui
  - service
  - data
```

只要求一条：左边的不能 import 右边的。

### Step 4 · 填验证命令

把真实命令写进 `ARCHITECTURE.md` 第 7 节，并同步到 `AGENTS.md`：

| 用途 | 示例 |
|---|---|
| 受影响测试 | `<你的命令> --changed` |
| 全量测试 | `<你的命令>` |
| 类型检查 | `<你的命令>` |
| lint | `<你的命令>` |
| 架构检查 | `<你的命令>` |
| 漂移检查 | `<你的命令>` |

命令不确定就先填「全量测试」和「lint」两条。

### Step 5 · 建第一个模块

```powershell
.\scripts\new-module.ps1 -Name order
```

然后填 `modules/order/MODULE.md` 和 `FLOW.md`，再到 `registry.yaml` 登记：

```yaml
modules:
  - name: order
    path: modules/order
    owner: <你>
    contract: modules/order/CONTRACT.md
    depends_on: []
```

### Step 6 · 上三条 CI

按 `ci/README.md` 配三条：依赖方向、循环依赖、未登记模块。

本地先跑一次：

```powershell
.\scripts\check-unregistered-modules.ps1
```

看到「模块登记检查通过」就算装完。

## 2. 第一次任务：完整走查

假设要做「订单取消」。

### ① 建任务目录

```powershell
.\scripts\new-task.ps1 -Id order-cancel -Title "订单取消" -Tier T2
```

生成 `specs/order-cancel/{intent,spec,plan}.md`。

### ② 对 AI 说

```text
按 docs/EXECUTION.md 执行 specs/order-cancel/ 下的 T2 任务。
先给分级和上下文清单，intent 和 spec 写完先给我确认，再写 plan。
```

### ③ AI 必须先回这五行

```text
分级：T2
读取：ARCHITECTURE.md / order.MODULE.md / order.FLOW.md / spec-cancel.md
      / payment.CONTRACT.md / src/order/cancel.ts
不读：user/** / report/**
假设：取消后不自动退款（未验证）
待确认：1) 是否需要发通知  2) 退款失败是否回滚取消
预算：≤4 模块，≤600 行
```

**这一步是验收 AI 有没有读流程的试金石。** 不输出这五行，直接叫停。

### ④ 回答待确认问题

一句话即可。没有待确认就回「按你的建议」。

### ⑤ AI 写 `intent.md` → 你确认

只看两件事：目标和非目标对不对；每条验收标准能不能变成一个测试。

### ⑥ AI 写 `spec.md` → 你确认

只看三件事：边界和失败路径全不全；有没有偷偷扩大范围；验收映射是不是每条都有验证方式。

### ⑦ AI 写 `plan.md` → 过 G1 计划门

只回答四个问题：

1. 改动面可接受吗？
2. 动了契约吗？
3. 影响模块漏了吗？
4. 回滚方式成立吗？

### ⑧ AI 开始实现

顺序必须是：**先写失败测试 → 确认失败 → 实现 → 变绿 → 补边界 → 重构**。

### ⑨ AI 交完成报告

```text
完成：<做了什么>
改动：<文件 + 行数>
验证：<命令 + 结果>
偏离：<与 plan 的差异>
风险：...
未做：...
```

### ⑩ 你合并

只看三件事：**契约有没有变、主流程有没有变、有没有新增依赖。**

代码写得漂不漂亮不归这道门管，那是测试和架构规则该管的。

## 3. 日常节奏

| 频率 | 做什么 |
|---|---|
| 每个任务 | 建任务目录 → 分级 → 上下文清单 → intent/spec/plan → 红绿重构 → 门禁 → 报告 |
| 每次提交 | G0 结构门自动跑 |
| 每次合并 | G2 合并门；人只看契约、主流程、依赖 |
| 每周 | 看一次架构 diff 和指标；把反复违反的规则升级成 CI |
| 每月 | 删一次 `ARCHITECTURE.md` 里过期的内容，保持一页纸 |

## 4. 三种接入方式

### A. 新项目

复制整个 `pack/`，按第 1 节走。

### B. 已有项目（渐进接入）

只复制：

```text
AGENTS.md
ARCHITECTURE.md
registry.yaml
docs/EXECUTION.md
templates/
modules/_template/
scripts/
```

然后：

1. 先按现有目录填 `registry.yaml`，不要为了框架改目录结构
2. 只上「未登记模块检查」一条 CI
3. 跑一周，再加「依赖方向检查」
4. 稳定后再加 spec 漂移检查

### C. 只想让 AI 遵守

只放 `AGENTS.md` 和 `docs/EXECUTION.md`，然后每次开新对话说：

```text
读 docs/EXECUTION.md，之后所有任务按它执行。
动手前先输出任务分级和上下文清单。
```

## 5. 脚本与生成规则

| 脚本 | 作用 |
|---|---|
| `new-module.ps1 -Name payment` | 从 `_template` 复制新模块，替换占位符 |
| `new-task.ps1 -Id order-cancel -Title "订单取消" -Tier T2` | 生成任务目录 |
| `check-unregistered-modules.ps1` | 检查 `modules/` 与 `registry.yaml` 是否一致 |

`new-task.ps1` 按级别生成：

| 级别 | 生成 | 为什么 |
|---|---|---|
| T0 | `plan.md`（含复现区） | 小改动只需要复现和失败测试 |
| T1 | `intent.md`、`spec.md` | 需要说清要什么，但不值得写计划 |
| T2 / T3 | `intent.md`、`spec.md`、`plan.md` | 跨模块，必须有人审计划 |

不使用 PowerShell 也可以手抄 `templates/` 里的模板，效果一样。

## 6. 常见问题

**Q：项目没有分层怎么办？**

不要为了框架重构。先在 `registry.yaml` 写一条最关键的约束，例如「`ui` 不能直接访问 `data`」。有一条就比没有强。

**Q：T0 和 T1 怎么快速判？**

看两个数：超过 50 行，或超过 1 个模块 → T1；都没超过 → T0。

**Q：小项目会不会太重？**

会。小项目只用三步：建任务目录、先写失败测试、跑 lint 和测试。其余模板空着不填。

**Q：AI 不按流程走怎么办？**

先确认 `AGENTS.md` 被编辑器加载。如果它还是不遵守，说明这条规则该变成 CI 检查，而不是继续在对话里强调。

**Q：多人怎么协作？**

`specs/` 下一个任务一个目录，互不冲突；`adr/` 共享；`ARCHITECTURE.md` 和 `registry.yaml` 必须走 PR 评审。

**Q：这个包要进 git 吗？**

要。它本身就是项目的一部分，尤其是 `ARCHITECTURE.md` 和 `adr/`，它们是项目的记忆。

**Q：AI 说某个类是死代码，能删吗？**

三证齐全才能删：静态无引用 + 运行时无注册（DI / 反射 / 路由 / 事件）+ 测试不依赖。缺一条只能标 `@deprecated`。

**Q：这套东西能保证不出 bug 吗？**

不能。它保证的是：错误在合并前暴露，漂移在架构上留痕，而不是悄悄积累。

## 7. 怎么判断这套流程真的生效了

- AI 每次任务开头都会输出「分级 + 上下文清单」
- 每个 PR 都能追到对应的 `intent.md` / `spec.md` / `plan.md`
- CI 里能看到架构规则检查，且失败时真的会拦住合并
- 每周的架构 diff 里没有未登记的跨层调用
