# 使用指南：装 CLI、填契约、跑第一个任务

## 0. 先判断要不要用

| 适合 | 不适合 |
|---|---|
| 会持续迭代一个月以上的项目 | 一次性脚本 |
| 需求会反复变 | 纯探索原型 |
| 出现过多轮修改后失控 | 需求还不存在的阶段 |
| 有第二个人要看代码 | 只跑一次的 demo |

小项目只做三件事：填 `guardrails.yaml`、保留常驻卡、跑 `verify` 章节。

## 1. 安装

```bash
python -m pip install -e /path/to/ai-dev-guardrails
guardrails --version
```

不装 CLI 也可以手工复制 `pack/`，但 `lint-manual`、`brief`、`sync`、`eval-routing` 就用不了。

## 2. 初始化

```bash
# 新项目：空目录，或只有 .git / .gitignore / README.md
guardrails init --target . --mode greenfield

# 老项目：只复制契约层和手册，不碰现有代码
guardrails init --target . --mode brownfield

# 先看会复制什么、哪些会冲突
guardrails init --target . --mode brownfield --dry-run
```

`greenfield` 会复制 `pack/` 的全部内容；目录里除 `.git`、`.gitignore`、`README.md` 之外还有文件时，需要 `--force`。

`brownfield` 只复制：`guardrails.yaml`、`manual/`、`templates/`、`specs/`、`acceptance/`、`ci/`、`eval/`、`lessons.md`、`ARCHITECTURE.md`、`modules/_template`。同名文件默认保留，`init` 会列出冲突；确认要覆盖才用 `--force`。

brownfield 不会覆盖 `AGENTS.md`、`.claude/`、`.cursor/`、`.kiro/`；需要 Claude Code hook 时，手动把 `pack/.claude/settings.json` 合并到现有配置。

## 3. 填 `guardrails.yaml`

只填五块：

```yaml
modules:
  - name: order
    path: modules/order
    layer: application
    owner: "@you"
    contract: modules/order/CONTRACT.md
    depends_on: [payment]

contracts:
  - id: http.order
    path: openapi/order.yaml
    kind: openapi

risk:
  unknown_default: R1   # 老项目建议改成 R2
  R3: [openapi/**, migrations/**, auth/**, package.json, pyproject.toml]
  R2: [modules/**]

commands:
  affected: "npm test -- --changed"
  full: "npm test"
  typecheck: "npm run typecheck"
  lint: "npm run lint"
```

`guardrails doctor` 会检查这四个命令是否还是 `TODO`。

## 4. 裁剪手册

常驻卡 `manual/00-card.md` 只放：

- 目标一句话
- 8–10 条红线
- 路由表
- 状态与验证命令

章节在 `manual/chapters/*/SKILL.md`，上限 6 个。每个章节必须有：

- `description`：什么时候用、什么时候不要用
- `when_to_use` / `when_not_to_use`
- `token_budget`

不用的章节直接删；新增章节必须先合并/删除一个，否则 `lint-manual` 失败。

```bash
guardrails lint-manual
guardrails sync
guardrails sync --check
```

## 老项目接入（brownfield）

老项目不要直接 `init --force`。按这个顺序：

1. 开分支、备份，打一个基线 tag。
2. `guardrails init --target . --mode brownfield --dry-run`，先看会复制什么、哪些会冲突。
3. 去掉 `--dry-run` 执行；冲突文件默认保留，手动合并。
4. 填 `guardrails.yaml`，描述现状而不是理想架构：
   - `layers` 从现有目录反推；
   - `modules` 只登记 top 5–8 个；
   - `contracts` 先留空，识别出公共 API 再填；
   - `commands` 用现有真实命令；
   - `risk.unknown_default: R2`，避免未登记文件被误判为 R1。
5. 建基线：

```bash
git tag baseline/before-guardrails
guardrails contract snapshot --path openapi/order.yaml --out .guardrails/contracts/order.json
guardrails test-lock --task baseline
```

6. 前 1–2 个任务只读：模块地图、公共契约、现有测试覆盖、characterization tests，不改业务行为。
7. 门禁渐进：第 1 周只上 `sync --check` + `affected`；第 2 周加 `contract diff`；稳定后再加 `quality --fail-on`。

注意：`test-lock` 目前是单个全局锁。基线锁之后不要同时跑多个任务；需要并行时先按任务拆锁文件。

## 原文、派生与生成

不要维护“原始目录 + AI 目录”两份都可写的副本，那会双源漂移。只保留一个可写源：

```text
原文层   specs/<id>/raw/ + git commit  只读、不可变
派生层   intent/spec/plan/state/trace  AI 可写，但必须引用原文
生成层   AGENTS.md / adapters / 规则    由 sync 单向生成，不手改
```

- 原始需求、issue、日志用 `guardrails raw add` 放进 `specs/<id>/raw/`，工具会记录来源、时间和 sha256。
- `trace.yaml` 的 `claims` 写结论 → `raw/` 或 `file:line`；`acceptance` 写验收标准 → 测试名。
- 压缩后 `guardrails state handoff --task <id>` 会带上 raw manifest 和 trace；先回读原文，再继续。
- 提交前跑 `guardrails verify-trace --task <id>`；CI 跑 `guardrails verify-trace --all`。
- `sync` 只覆盖带 generated 标记的文件；遇到手写同名文件会报冲突，确认后再 `sync --force`。

## 5. 第一个任务

```bash
guardrails task new --id order-cancel --title "订单取消" --type feature --risk R3 \
  --files modules/order/src/cancel.ts openapi/order.yaml
```

生成 `specs/order-cancel/{task.yaml,intent.md,spec.md,plan.md}`，以及 `raw/manifest.json` 和 `trace.yaml` 骨架。

把原始需求放进 `raw/`，并让工具记录 sha256：

```bash
guardrails raw add --task order-cancel --from ./issue.md --origin "issue #123"
guardrails raw list --task order-cancel
```

生成的 `raw/manifest.json` 形如：

```json
{
  "task": "order-cancel",
  "captured_at": "2026-11-18T12:00:00+08:00",
  "sources": [
    {"path": "raw/issue.md", "origin": "issue #123", "sha256": "..."}
  ]
}
```

`trace.yaml` 同时写验收映射和原文引用：

```yaml
acceptance:
  - criterion: 用户可以取消未支付订单
    test: tests/order/test_cancel.py::test_cancel_unpaid
claims:
  - id: C1
    claim: 取消后不自动退款
    source: raw/issue.md
    lines: "12-18"
    sha256: "..."
```

然后：

```bash
guardrails brief --task specs/order-cancel/task.yaml
guardrails state init --task order-cancel --task-file specs/order-cancel/task.yaml
```

输出：

```text
selected: change, review, verify
risk: R3
reason: type=feature; risk=R3; R3 path: openapi/order.yaml
tokens: ~3800 / 4000
raw sources:
- raw/request.md (issue #123)
manifest: ...
```

只加载这三个章节。不要读 `manual/` 里的其他章节。

## 6. 日常节奏

| 时机 | 命令 |
|---|---|
| 任务开始 | `guardrails task new ...` + `guardrails brief --task specs/<id>/task.yaml` + `guardrails state init --task <id>` |
| 每步 | `guardrails state next --task <id> --next "..." --chapter <id>` |
| 压缩后 | `guardrails state handoff --task <id>`，按 raw manifest 回读原文 |
| 改代码前 | `guardrails affected --diff`，只跑受影响测试 |
| red 确认后 | `guardrails test-lock --task <id>` |
| 改测试前 | `guardrails test-approve --task <id> --reason ...` |
| 提交前 | `guardrails sync --check` + `guardrails verify-trace --task <id>` + `guardrails quality --diff --fail-on` |
| 合并前 | `guardrails run full` + `guardrails contract diff --base <snapshot> --current <path>` + `guardrails test-check --task <id>` |
| 发布前 | `guardrails card --task <id>` + `review` 章节 |
| 每周 | `guardrails eval-routing` + `guardrails report` + `guardrails metrics report` |
| 模型/规则升级后 | `guardrails canary`；对比基线，确认没有回归 |

## 7. CI

把 `pack/ci/gates.yml` 复制到 `.github/workflows/gates.yml`。它会跑：

1. `guardrails lint-manual`
2. `guardrails sync --check`
3. `guardrails verify-trace --all`
4. `guardrails run affected|full|typecheck|lint`

契约 diff 在 `gates.yml` 里有注释示例，启用快照后取消注释。

## 8. 运行时保护（Claude Code）

`guardrails init` 会把 `.claude/settings.json` 一起复制进来。已有的项目手动合并：

```bash
guardrails doctor
```

它会：

- 在 `Edit/Write` 前拦截 `ARCHITECTURE.md`、`guardrails.yaml`、`manual/**`、`adr/**`、`specs/**/raw/**`、CI 配置。
- 在 `Bash` 前拦截 `rm -rf`、`curl | sh`、`git push --force`、`git reset --hard` 等。
- 在压缩后重新注入“先读 AGENTS.md、先跑 brief”的提示。

hook 通过 stdin 接收 JSON；`guardrails hook --event pre-tool` 在项目根目录运行。

## 9. 常见问题

**Q：章节应该写多长？**
每个章节 900–1400 tokens 以内。超预算先删例子，再把细节移到 `references/`。

**Q：为什么不能把所有流程写进 AGENTS.md？**
隐式路由会塌缩：skill 库越大，agent 越可能什么都不加载。常驻卡只放路由和红线，流程放章节。

**Q：AI 不按 `brief` 加载怎么办？**
先确认 `AGENTS.md` 被编辑器加载；仍然不遵守，就把“必须加载 manifest 章节”做成 hook/CI 检查，而不是继续在对话里强调。

**Q：小项目会不会太重？**
会。小项目只保留常驻卡 + `verify` 章节，其他章节删掉；`guardrails.yaml` 的 modules 可以先留空。

**Q：和 SpecGuard / AGT / harn 什么关系？**
SpecGuard 管 spec/test 状态机，AGT/Caper 管运行时策略，harn 给 harness 打分；本仓库只管架构契约、章节路由和契约证据。

**Q：为什么还要 `raw/`？git 不是已经保存历史了吗？**
git 保存的是代码历史；原始需求、issue、日志、截图、API 响应通常不在 git 里。`raw/` 固定这些不可变输入，代码仍然用 commit/worktree 作为原文锚点，不复制整个仓库。

**Q：能不能保留“原始目录 + AI 目录”两份都可写？**
不要。两份都可写会在几周内漂移，最后不知道哪份是真的。只保留一个可写源：原文只读、派生可写、生成物不手改。

**Q：这套东西能保证不出 bug 吗？**
不能。它保证的是：错误在合并前暴露，漂移在架构上留痕，上下文不会无限膨胀。
