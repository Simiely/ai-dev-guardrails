# 双轨框架：上轨定边界，下轨验结果，中间自由发挥

## 问题：单点方案治不了长期退化

提示词、单测、代码审查都是单点。它们各自有效，但管不住同一件事：**每一轮改动都局部合理，累计起来却让系统越来越难改。**

AI 的默认行为是优化「这次 diff 看起来对」，不是「三个月后还能改」。所以解法不能是更严的提示词，而必须是把「边界」和「验收」变成结构。

## 三层结构

```text
上轨  宪法层   模块边界 / 依赖方向 / 公共契约 / 安全与数据边界
中区  制品链   intent → spec → plan → code + tests
下轨  证据层   测试 / 类型 / lint / 架构规则 / spec 漂移
```

### 上轨：唯一不允许 AI 自由改动的地方

只装五类内容：

1. 模块清单与依赖方向
2. 公共契约（API、事件、数据模型、错误码）
3. 数据与安全边界
4. 质量底线
5. 禁止清单

产物是 `ARCHITECTURE.md`、`registry.yaml` 和 `adr/`。**AI 可以提议修改，但不能自己改。**

这一条把「漂移」从「悄悄发生」变成「必须显式申请」。

### 中区：制品链

每个阶段一个版本控制的文件，下一阶段只读上一阶段：

| 阶段 | 产物 | AI 的自由度 | 完成判据 |
|---|---|---|---|
| 意图 | `intent.md` | 帮你问清楚，不许自己加需求 | 目标、非目标、约束齐全 |
| 规格 | `spec.md` | 可以提方案，契约要人确认 | 验收标准可测试 |
| 计划 | `plan.md` | 自由拆解 | 改动面、影响模块、风险点列全 |
| 实现 | `diff + tests` | 完全自由 | 门禁全绿 |
| 评审 | `review.md` | 可以自查，不能自批 | 人工 code owner 通过 |

硬规则：**实现偏离计划时，`plan.md` 与 diff 必须同一次提交。**

### 下轨：四道门

| 门 | 时机 | 检查 | 失败后果 |
|---|---|---|---|
| G0 结构门 | 每次提交 | 依赖方向、循环依赖、分层越界、禁止目录、未登记模块 | 阻断 |
| G1 计划门 | 动手前 | 是否跨模块、是否动契约、改动面是否超标 | 大改动阻断 |
| G2 合并门 | PR | 受影响测试、全量回归、契约测试、漂移检查 | 阻断 |
| G3 发布门 | 上线 | 风险分级、灰度、回滚预案 | 高风险需签核 |

三条执行原则：

- 能机器判的，绝不写成提示词
- 通过时静默，失败时把堆栈、diff、期望值全喂回去
- 人工只守不可逆的点：改契约、改数据、上线

## 自由度分三档

这是「框架内可以随意发挥」能成立的原因。

| 档位 | 范围 | 机制 |
|---|---|---|
| 自由 | 函数内部实现、算法选择、私有命名、局部重构、测试写法 | 不看过程，只看门禁 |
| 声明 | 跨模块调用、新增文件、改公共函数签名、改配置项 | 在 `plan.md` 列出，人扫一眼 |
| 批准 | 新增依赖、新增模块、改数据模型、改对外 API、改安全策略 | ADR + 人批 + registry 登记 |

日常九成代码落在「自由」档，因为它们不碰边界。

## 为什么这样能稳住

- **上下文有边界**：每次只装配当前模块、当前 spec、一跳契约，不让 AI 读全仓库。
- **意图有载体**：计划、规格、决策都在仓库里，不依赖聊天记录。
- **错误有出口**：测试、类型、架构规则、漂移检查在合并前给出一致的判定。
- **结构有惯性**：模块边界和依赖方向由机器守着，单次改动无法悄悄破坏。

## 代价与边界

- 前期会变慢，写 spec 和 plan 是额外工作。
- 小任务上全套流程会显得荒谬，所以必须按 T0–T3 分级。
- 它不能让 AI 不出错，只能让错误在合并前暴露、在架构上留下痕迹。
- 不适用：一次性脚本、纯探索原型、需求还不存在的阶段。
