# 架构契约层：常驻卡、显式路由与渐进披露

## 问题：单点方案治不了长期退化

提示词、单测、代码审查都是单点。它们各自有效，但管不住同一件事：**每一轮改动都局部合理，累计起来却让系统越来越难改。**

AI 的默认行为是优化「这次 diff 看起来对」，不是「三个月后还能改」。所以解法不能是更严的提示词，而必须是把「边界」和「验收」变成结构。

## 三层结构

```text
上轨  契约层   模块边界 / 依赖方向 / 公共契约 / 风险分级
中区  手册层   常驻卡 + 6 个章节；按任务显式加载 1–3 个
下轨  证据层   测试 / 类型 / lint / 架构规则 / 契约快照 / routing eval
```

### 上轨：架构契约

唯一机器源是 `guardrails.yaml`：模块、层、依赖、契约、保护路径、风险规则、验证命令。人看的 `ARCHITECTURE.md` 是它的视图，不是第二份真相。

AI 可以提议修改，但不能自己改。生产项目里，这一条应该由 hook/CI 守，而不是靠提示词。

### 中区：手册编译器 + 显式路由

`manual/00-card.md` 是常驻卡，只放四类内容：

1. 目标（一句话）
2. 红线（8–10 条，全部是「不得/必须」，每条有检查）
3. 路由表（任务类型 / 文件 → 章节）
4. 状态与命令（`state.json`、验证命令）

`manual/chapters/*/SKILL.md` 是 6 个章节，每个章节都有：

- `description`：什么时候用、什么时候不要用
- `when_to_use` / `when_not_to_use`
- `globs` / `inputs` / `outputs` / `checks`
- `token_budget` / `related`

`guardrails brief` 是**显式路由器**，不是让 AI 自己翻目录。它按任务类型、文件 glob、风险等级预选 1–3 个章节，输出 manifest、token 预算和跳过理由；选不出来就让人选，绝不静默零加载。

### 下轨：证据门禁

- `guardrails sync --check`：生成视图是否过期。
- `guardrails contract diff`：破坏性契约变更。
- `guardrails risk --diff`：R0–R3。
- `guardrails lint-manual`：章节质量、重复、条件句、弱路由。
- `guardrails eval-routing`：routing recall、zero-load、over-load。
- 质量内核：`affected`（受影响测试）、`test-lock`/`test-check`（测试托管）、`quality`（复杂度/重复）、`mutation`（改动行变异）、`card`（后果卡）。
- 运行证据：`metrics`（JUnit/本地 ledger）、`report`（结构信号 + 指标）、`canary`（基线回归对比）。
- 测试 / 类型 / lint（项目命令由 `guardrails run` 执行）。

## 为什么不是一份大手册

2026 年的证据指向同一个结论：**上下文不是越多越好，规则不是越厚越有效。**

| 证据 | 数字 | 设计含义 |
|---|---|---|
| [Lost in Implicit Routing](https://arxiv.org/abs/2610.18522) | 1,000 个无关 skill → 召回 73.6%→27.4%，零加载 9.3%→51.6%；显式预选保持 73.9% | 必须显式预选，不能靠 AI 自己翻目录 |
| [SkillsBench](https://arxiv.org/abs/2602.12670) | 精选 skill 平均 +16.2pp，但 16/84 个任务变差；2–3 个模块最优 | 章节要少、要验证；不要让 AI 自己写章节 |
| [138K SKILL.md 缺陷研究](https://arxiv.org/abs/2608.08453) | 91.8% 至少一个缺陷；主要是弱路由元数据、正文臃肿、资源组织差 | 必须有 `lint-manual` |
| [SkillJuror](https://arxiv.org/abs/2606.11543) | 渐进披露让资源触碰 1.18→3.85，验证通过 +4.1%；任务相关 | 对实现/检查/修复有帮助；精确格式/阈值放测试 |
| [Guardrails Beat Guidance](https://arxiv.org/abs/2604.11088) | 5,000+ runs；负向约束一致有益，正向指令可能有害；0–50 条规则内稳定 | 红线用「不得」，流程用机器检查；不要靠堆正向指令 |
| [McMillan](https://arxiv.org/abs/2605.10039) | 每多生成一个函数，遵守 odds 约降 5.6% | 长任务切会话；压缩后只恢复卡 + 当前章节 |

## 自由度分三档

| 档位 | 范围 | 机制 |
|---|---|---|
| 自由 | 函数内部实现、算法选择、私有命名、局部重构、测试写法 | 不看过程，只看门禁 |
| 声明 | 跨模块调用、新增文件、改公共函数签名、改配置项 | `plan.md` 列出，人扫一眼 |
| 批准 | 新增依赖、新增模块、改数据模型、改对外 API、改安全策略 | ADR + 人批 + 契约快照 diff |

## 代价与边界

- 前期会变慢：写章节、填 `guardrails.yaml`、跑 routing eval。
- 小任务上全套流程会显得荒谬，所以按类型/文件数/完整性选择性使用。
- 它不能让 AI 不出错，只能让错误在合并前暴露、在架构上留下痕迹。
- 不适用：一次性脚本、纯探索原型、需求还不存在的阶段。
- 章节/规则有保质期：模型升级后要跑 canary，删掉不再有效的规则。

## 证据强度

- **强对照**：Guardrails Beat Guidance、SkillsBench、Lost in Implicit Routing、138K SKILL.md、TDAD、SpecBench、SlopCodeBench。
- **实践/工具**：Claude Code Skills、Kiro steering、Cursor rules、SpecGuard、Microsoft AGT、Caper。
- **弱/预印本**：Correa 单操作者实录、Caper、Oracle Drift、SGE；结论应在本项目复验。
- **没有单一研究证明“这套完整框架”有效**。所以内置 `eval-routing` 和 canary，让框架可证伪。
