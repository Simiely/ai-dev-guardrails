# 双轨框架 · 执行说明

> 版本 v1.0 ｜ 适用对象：AI 编码 Agent + 人类负责人
> 这是操作手册，不是理念介绍。安装步骤与文件说明见 `README.md`。

---

## 0. 快速执行卡

每次任务只做这 8 步：

```
分级 → 装上下文 → 写 intent（T1+）→ 写 spec（T1+）
→ 写 plan（T2+）→ 红-绿-重构 → 跑门禁 → 交完成报告
```

三条铁律，任何时候不得违反：

1. **不确定就问，不许猜。** 猜的必须写进"假设"栏，标注未验证。
2. **不许为了让检查通过而改检查。** 测试挂了，先证明是实现错还是断言错。
3. **不许扩大改动面。** 顺手看到的问题写进"发现"栏，不顺手改。

---

## 1. 使用方式与优先级

| 对象 | 怎么用 |
|---|---|
| AI | 每次任务开始，完整读第 1–5 节；动手前必须输出"分级 + 上下文清单" |
| 人 | 只看第 5 节的门禁清单、第 6 节的检查表、第 10 节的周复盘 |
| CI | 只执行第 5 节的机器检查，不做判断 |

**优先级**：`ARCHITECTURE.md` > 本文件 > `AGENTS.md` > 任务描述 > AI 的默认习惯。

本文件与 `ARCHITECTURE.md` 冲突时，以 `ARCHITECTURE.md` 为准，并立即停下报告冲突点。

---

## 2. 角色与权限

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| 人（Owner） | 定宪法、批契约、批上线、调整分级、改门禁 | 口头让 AI 跳过门禁 |
| AI（执行者） | 读代码、写代码、写测试、跑检查、提方案、提 ADR | 改宪法、改 registry、新增依赖、放宽断言、删测试、改 CI 配置、自批 PR |
| 机器（裁判） | 执行规则，给出通过/失败 | 不做主观判断 |

**AI 的三条绝对禁令：**

- 不修改 `ARCHITECTURE.md`、`registry.yaml`、`adr/`、CI 配置文件。
- 不删除或跳过任何测试来让流水线变绿。
- 不使用 `@ts-ignore`、`eslint-disable`、`noqa`、`#[allow(...)]` 之类的手段绕过检查。

需要其中任何一项时，停下来，写一份提案，等人批准。

## 3. 任务分级（先分级，再动手）

### 3.1 判定问题

按顺序问四个问题，命中任何一条就升级：

1. 要改对外契约（API、事件、数据模型、错误码）吗？→ **T3**
2. 要新增模块或新增第三方依赖吗？→ **T3**
3. 会碰到 2 个以上模块吗？→ **T2**
4. 改动超过 50 行或 1 个模块吗？→ **T1**，否则 **T0**

### 3.2 分级表

| 级别 | 典型任务 | 必做产物 | 改动面预算 | 门禁 |
|---|---|---|---|---|
| **T0** | 改文案、修 typo、单点 bug | 复现步骤 + 失败测试 | ≤1 模块，≤50 行 | G0、G2 |
| **T1** | 小功能增量、单模块增强 | intent + 一页 spec + 测试 | ≤2 模块，≤200 行 | G0、G2 |
| **T2** | 新功能、跨模块改动 | intent + spec + plan | ≤4 模块，≤600 行 | G0、G1、G2 |
| **T3** | 改契约、改数据模型、新模块、新依赖 | 全套 + ADR + 人批 | 不设上限，必须拆 | 全部 |

**超出预算时的唯一正确动作：拆任务。** 拆不动就升级分级，不要硬做。

## 4. 标准执行流程

### Step 0 · 装配上下文

- **输入**：任务描述。
- **动作**：按第 5 节的装配规则列清单，输出给用户。
- **产出**：上下文清单（T0 可省略确认，T1+ 必须确认）。
- **判据**：清单里的每个文件都真实存在，且已经读过。
- **禁止**：全库 grep 当上下文、读兄弟模块实现、凭记忆补全。

### Step 1 · 判定分级

- **产出**：级别 + 判定理由 + 改动面预算。
- **判据**：四个判定问题都有明确答案。
- **禁止**：先写代码，再补分级。

### Step 2 · 写 `intent.md`（T1+）

- **内容**：目标 / 非目标 / 约束 / 验收标准。
- **判据**：每条验收标准都能直接翻译成一个测试。
- **禁止**：自己加需求、自己扩大范围、把"怎么做"写进意图。

### Step 3 · 写 `spec.md`（T1+）

- **内容**：行为规格、接口契约、边界与失败路径、明确不做什么。
- **判据**：每条验收标准在 spec 里都有对应的验证方式。
- **禁止**：写实现细节（那是 plan 的事）。

### Step 4 · 写 `plan.md`（T2+）

- **内容**：任务拆解（每步一个可验证结果）、改动文件清单、影响模块、回滚方式、风险点。
- **判据**：一个没看过本次对话的工程师，能照着做完。
- **门禁**：G1 计划门通过后，才能写第一行代码。

### Step 5 · 实现

固定顺序，不许颠倒：

1. 先写失败测试或复现脚本，**确认它确实失败**。
2. 再实现，让测试变绿。
3. 补边界与失败路径测试。
4. 重构（只在全绿的前提下，且不改变行为）。

实现纪律：

- 一次只做 `plan.md` 里的一步。
- 不新增 plan 之外的文件。
- 不修改 plan 之外的模块。
- 需要偏离 plan 时：**停下 → 更新 plan.md → 再继续**，两者必须在同一次提交里。

### Step 6 · 自检

按顺序跑，前一条不过不跑后一条：

```bash
# 命令按项目实际替换，并写进 ARCHITECTURE.md 的"验证命令"一节
<受影响测试>
<全量测试>
<类型检查>
<lint>
<架构规则检查>
<spec 漂移检查>
```

失败处理见第 9 节。**不许反复重试同一种写法。**

### Step 7 · 交付

输出固定格式的完成报告（模板见 8.6），并附 PR 描述。

PR 必须包含：intent 链接、plan 链接、验证结果、偏离说明、风险、回滚方式。

### Step 8 · 复盘

把本次踩的坑写进 `lessons.md`，一行一条，不写感受，只写事实和下次怎么做。

同一类问题出现两次 → 提议把它升级成机器检查。

## 5. 上下文装配规则

### 5.1 必读（按这个顺序）

1. `ARCHITECTURE.md`（根不变量）
2. 当前模块的 `MODULE.md`
3. 当前模块的 `FLOW.md`
4. 当前任务的 `spec.md`（如有）
5. 直接依赖模块的 `CONTRACT`（**只读契约，不读实现**）
6. 当前模块里要改的具体文件

### 5.2 禁读

- 兄弟模块的实现代码
- 传递依赖（依赖的依赖）
- 与本次任务无关的目录
- 全库搜索结果直接当上下文

### 5.3 读不够怎么办

不许猜。输出"待确认问题清单"：

- 最多 3 个问题。
- 每个问题必须附上你的默认建议，让人可以一句话确认。
- 人没回答之前，不动手写代码。

### 5.4 上下文清单格式（每次任务开头必须输出）

```
分级：T2
读取：ARCHITECTURE.md / order.MODULE.md / order.FLOW.md / spec-cancel.md
      / payment.CONTRACT.md / src/order/cancel.ts
不读：user/** / report/**
假设：取消后不自动退款（未验证）
待确认：1) 是否需要发通知  2) 退款失败是否回滚取消
预算：≤4 模块，≤600 行
```

这五行是给人看的审计入口。写不出来，说明还没准备好动手。

## 6. 四道门的操作细则

### G0 · 结构门（每次提交，机器执行）

检查项：

- 依赖方向是否单向
- 是否存在循环依赖
- 是否 import 了其他模块的内部文件
- 是否修改了禁止目录
- 新模块是否已在 `registry.yaml` 登记

失败时：修到通过为止。**不许注释掉规则、不许加 ignore、不许改检查脚本。**

### G1 · 计划门（T2+，人执行）

人只回答四个问题：

1. 改动面是否可接受？
2. 是否动了契约？
3. 影响模块有没有漏？
4. 回滚方式是否真的成立？

四个都是"是/否"或一句话，不需要读代码。通过才开工。

### G2 · 合并门（PR，机器 + 人）

机器检查：

- 受影响测试
- 全量测试
- 契约测试
- spec 漂移检查
- 覆盖率不下降

人只看三件事：

1. 契约有没有变
2. 主流程有没有变
3. 有没有新增依赖

**写代码的 AI 不能批准自己的 PR。**

### G3 · 发布门（上线，人执行）

| 风险 | 判定条件 | 要求 |
|---|---|---|
| 低 | 单模块、无契约变更、测试齐全 | 正常发布 |
| 中 | 跨模块，或有配置变更 | 灰度 10%，观察核心指标 |
| 高 | 契约、数据、安全相关 | 灰度 + 回滚演练 + 明确签核人 |

## 7. 检查清单

### 7.1 动手前 8 问

1. 分级对不对？
2. 上下文清单齐不齐？
3. 验收标准能不能写成测试？
4. 要改的文件列全了吗？
5. 有没有碰到契约？
6. 有没有更简单的做法？
7. 需要新增依赖吗？（是 → T3）
8. 回滚方式是什么？

### 7.2 提交前 10 项

1. 失败测试确实先红后绿
2. 全量测试通过
3. 类型检查通过
4. lint 通过
5. 架构规则通过
6. 没有新增未登记依赖
7. 没有改测试断言来迁就实现
8. `plan.md` 已同步
9. 没有顺手改无关代码
10. 完成报告已填

### 7.3 评审时人看 8 项

1. 契约有没有变
2. 主流程有没有变
3. 分支有没有漏测
4. 失败路径有没有兜底
5. 有没有新增依赖
6. 有没有隐式状态或全局副作用
7. 死代码是删了还是留着，依据是什么
8. 回滚是否可行

## 9. 常见违规与正确做法

| 违规行为 | 正确做法 |
|---|---|
| 测试挂了就改断言 | 先判定是实现错还是断言错，写出证据 |
| 顺手重构 | 记进"发现"栏，另开任务 |
| 加兼容层 / shim | 先问旧路径能不能删；不能删才加，并登记 |
| 直接加依赖 | 走 T3 + ADR |
| 判定是死代码就删 | 三证齐全：静态无引用 + 运行时无注册 + 测试不依赖 |
| 先实现再补测试 | 只有 T0 允许，且必须补 |
| 上下文不够就猜 | 输出待确认问题，等人回答 |
| 用 ignore 注释绕过检查 | 禁止，必须修根因 |
| 一次改多个模块 | 拆任务 |
| 自己批准自己的 PR | 禁止 |

## 10. 卡住了怎么办

同一个问题失败 **2 次**，立即停止重试，输出四件事：

1. 试过什么（含命令和完整报错）
2. 现在的判断（根因假设）
3. 三个候选方案及各自代价
4. 需要人决定的那一件事

禁止：

- 换着写法反复试
- 扩大改动面去找"能跑"的版本
- 删测试或放宽断言求绿

## 11. 周复盘

每周只看趋势，不看单点：

| 指标 | 目标方向 |
|---|---|
| 变更失败率 | ↓ |
| 回归率 | ↓ |
| 两周返工率 | ↓ |
| 重复代码块 | ↓ |
| 架构规则违反 | = 0 |
| spec-code 漂移 | = 0 |
| 单 PR 触及模块数 | ≤ 2 |
| 平均上下文包大小 | ↓ |

两条维护规则：

- **规则升级**：同一条规则被违反 2 次 → 从提示词搬进 CI。
- **文档瘦身**：`ARCHITECTURE.md` 超过一页就删，`AGENTS.md` 超过 200 行就删。

## 12. 接入现有项目（最小启动包）

### 12.1 目录

```
ARCHITECTURE.md          一页纸：边界、依赖方向、契约、禁止项、验证命令
registry.yaml            模块登记表
AGENTS.md                只放指针和红线，控制在 200 行内
docs/EXECUTION.md        本文件
adr/                     架构决策记录
modules/<name>/
  MODULE.md
  FLOW.md
  CONTRACT.md
  src/
  tests/
specs/                   每次任务的 intent / spec / plan
lessons.md               复盘记录
```

### 12.2 `AGENTS.md` 只放这些

```markdown
# 项目红线

- 动手前必须读 docs/EXECUTION.md，并按第 4 节输出分级与上下文清单。
- 不得修改 ARCHITECTURE.md、registry.yaml、adr/、CI 配置。
- 不得删除或跳过测试，不得使用 ignore 注释绕过检查。
- 跨模块只能 import 对方的 CONTRACT，不得 import 内部文件。
- 新增依赖、新增模块、改契约：停下，提 ADR，等人批准。

# 验证命令
- 单测：<command>
- 全量：<command>
- 类型：<command>
- lint：<command>
- 架构：<command>
```

### 12.3 第一批 CI 检查（三条就够）

1. 依赖方向：禁止反向 import、禁止跨模块 import 内部文件
2. 循环依赖：检测到即失败
3. 未登记模块：`registry.yaml` 里没有的模块目录，直接失败

先上这三条，再补测试和漂移检查。

## 13. 这套说明本身怎么维护

- 本文件只写"怎么做"，不写"为什么"。为什么在《双轨框架》里。
- 每次发现 AI 理解错的地方，改的是本文件的措辞，不是反复在对话里强调。
- 每次新增一条规则，先问：这条能不能变成机器检查？能，就别只写在这儿。
